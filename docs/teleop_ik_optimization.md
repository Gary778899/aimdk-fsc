## 1. 核心机制

宇树通过三个不同节拍处理手柄输入频率高于 IK 吞吐的问题：输入进程持续覆盖最新状态，主循环采样并同步求解 IK，独立控制线程持续发布最近一次关节目标。

```text
XR 手柄输入事件
      │
      ▼
TeleVuer 独立进程
覆盖最新位姿与按键状态
      │ 共享内存
      ▼
遥操主循环（默认目标 30 Hz）
读取最新输入 → 读取关节反馈 → 双臂 IK → 更新关节目标
      │ 带锁的目标变量
      ▼
G1_29 控制线程（目标 250 Hz）
读取最近目标 → 按反馈与速度限制调整发送位置 → 发布命令
```

| 环节 | 调度方式 | 上一环节更新较慢时的行为 |
| --- | --- | --- |
| 输入接收 | 独立进程处理 XR 事件，覆盖共享数组和标量 | 缓存保留各字段最近一次收到的值 |
| IK 求解 | 主循环同步求解，默认目标 30 Hz | 没有新输入也可再次读取已有状态；求解超时则主循环实际降频 |
| 命令发布 | G1_29 独立线程，目标 250 Hz | 继续使用最近一次写入的关节目标与前馈力矩 |

这套结构避免在 IK 消费层排队补算历史位姿。已开始的求解仍需执行完毕，因此求解本身的耗时仍会形成跟随延迟。

## 2. 输入接收：覆盖最新状态

TeleVuer 使用 `multiprocessing.Process` 运行 Vuer 服务，通过带锁的 `Array` 和 `Value` 与主进程共享输入。

`on_controller_move()` 收到手柄事件后，分别覆盖 `left_arm_pose_shared`、`right_arm_pose_shared` 以及扳机、Grip、按钮和摇杆字段。位姿读取属性从当前共享数组复制数据；主循环通过 `get_tele_data()` 获取转换后的输入。

IK 消费端没有保存每个输入帧的 FIFO 队列。求解期间收到的中间位姿可以被后续事件覆盖，下一轮读取时直接取得当时可用的最新值。

例如，假设输入为 90 Hz、IK 实际为 20 Hz：一次求解期间可能收到四五次更新，下一次求解采样最新状态，中间位姿不逐一补算。该频率组合仅用于说明机制，未测量实际手柄发送频率。

并发边界是各共享字段的独立锁；左右位姿、头部和按键依次读写。该实现的最新状态缓存不提供整帧原子快照保证。

源码依据：[TeleVuer 输入接收、共享内存及读取属性](https://github.com/unitreerobotics/televuer/blob/main/src/televuer/televuer.py)、[TeleVuer 输入转换](https://github.com/unitreerobotics/televuer/blob/main/src/televuer/tv_wrapper.py)。

## 3. IK 主循环：按实际吞吐采样

`teleop_hand_and_arm.py` 中的 `--frequency` 默认值为 `30.0`，同时作为主循环控制与记录的目标频率。每轮主要顺序为：

1. 调用 `tv_wrapper.get_tele_data()` 读取输入。
2. 读取机器人当前双臂关节位置与速度。
3. 同步调用 `arm_ik.solve_ik()` 求解左右臂目标。
4. 调用 `arm_ctrl.ctrl_dual_arm()` 更新关节目标和前馈力矩。
5. 完成本轮记录等工作后，按剩余周期时间等待。

等待时间为：

```python
sleep_time = max(0, (1 / args.frequency) - time_elapsed)
```

当整轮耗时超过默认周期约 33.3 ms 时，等待时间为零，主循环立即进入下一轮。实际频率受 IK 和同一循环内其他工作共同限制。

该路径使用单个同步 IK 调用，没有求解任务并发、当前求解抢占或超时后自动换用更新目标的调度。新的手柄状态要到下一轮读取时才进入 IK。

源码依据：[主循环、默认频率和周期等待](https://github.com/unitreerobotics/xr_teleoperate/blob/main/teleop/teleop_hand_and_arm.py)。

## 4. 命令发布：独立使用最近一次 IK 结果

G1_29 控制器设置 `control_dt = 1.0 / 250.0`，创建独立发布线程。`ctrl_dual_arm()` 在锁内更新 `q_target` 和 `tauff_target`；`_ctrl_motor_state()` 每轮读取这两个目标并发布。

真机路径通过 `clip_arm_q_target()`，按当前关节反馈、速度限制和 `control_dt` 调整发送位置；仿真路径直接使用目标位置。因此，IK 尚未更新时，控制线程继续使用已有目标，发送位置也可能随关节反馈变化。

250 Hz 是该线程的目标发布频率；线程同样通过扣除本轮耗时后的等待控制节拍，实际频率需要运行测量。末端目标更新率由 IK 主循环决定，发布线程不会生成新的末端目标或补算手柄历史轨迹。

源码依据：[G1_29 控制器与发布线程](https://github.com/unitreerobotics/xr_teleoperate/blob/main/teleop/robot_control/robot_arm.py)。

## 5. IK 计算量与平滑处理

G1_29 的 `robot_arm_ik.py` 使用 Pinocchio、CasADi 和 IPOPT，主要处理如下：

- 锁定非双臂关节，建立缩减模型。
- 初始化时建立符号计算和优化问题，每轮更新左右末端目标参数。
- IPOPT 设置 `max_iter = 30`，启用 `warm_start_init_point` 选项。
- 主循环传入当前关节反馈，`solve_ik()` 将其用于求解初值和平滑参考。
- 优化目标包含关节变化平滑项，结果再经过权重为 `[0.4, 0.3, 0.2, 0.1]` 的四点加权滤波。

这些措施分别控制计算规模、迭代和输出连续性。最大迭代数不提供固定毫秒数的求解期限；平滑滤波也不增加 IK 吞吐。

源码依据：[G1_29 IK 初始化、求解选项与结果滤波](https://github.com/unitreerobotics/xr_teleoperate/blob/main/teleop/robot_control/robot_arm_ik.py)。

## 6. 当前 X2 实现与差异

输入与映射由 `remote_control` 承担，IK、调度及执行由 `aimdk_functions` 承担。
既有行为以[现场输入与执行说明](../overlay/src/functions/README.md#现场只读ik与统计)为主，
输入格式见[遥操输入包说明](../overlay/src/remote_control/README.md)，阶段状态见[第二阶段文档](dev_teleop_part2.md)。
遥操执行的关节跟踪误差现已改为仅观测，超5°继续发布；字段和验收以功能包现场执行说明为准。
最新完整执行会话已覆盖该行为，关节与TCP误差的比较口径见[误差依据](dev_teleop_part2.md#最近跟随误差的已知依据)；当前版本仍待完整回归。

2026-11-03 首次执行日志显示，原 FIFO 方案输入约 75 Hz、实际消费约 25 Hz，
接管后事件积压到 35 个，输入到结果约 519 ms，触发 0.5 秒时限。
日志目录为 `log/teleop_20261103_194556/`；该结果属于优化前版本。
据此已实现以下结构，已有容器执行记录，完整回归与性能基线待补充：

```text
SDK 回调 FIFO
      │
      ▼
独立接收线程：完整录制、逐帧校验
      ├── 普通位姿：单槽最新完整双手柄帧 ── 20 Hz 上限 ──┐
      └── Grip 边沿：完整帧 FIFO ── 优先处理参考与保持 ──┤
                                                        ▼
                                               主线程同步映射与 IK
                                                        │ 原子提交
                                                        ▼
                                               最新已接受双臂理想目标
                                                        │
                                                        ▼
                                               ROS 线程：50 Hz 发布
```

| 对照项 | 宇树参考 | 当前 X2 实现及后续方向 |
| --- | --- | --- |
| 最新输入 | 分字段覆盖共享内存 | 保持完整双手柄快照及 Grip 边沿保序 |
| 求解节拍 | 默认目标 30 Hz，超期后直接进入下一轮 | 普通位姿上限 20 Hz，取最新值且不补算；当前频率先完成验证 |
| 求解状态 | 模型初始化复用，实际关节作为初值和平滑参考 | 已复用模型、上一理想关节、SEW 和分支；继续减少重复 FK |
| 发布节拍 | 独立线程目标 250 Hz | 原生上肢接口 50 Hz；优化线程间阻塞 |
| 输入隔离 | 独立进程 | 当前为线程；满足第 9 节条件后评估进程隔离 |
| 平滑 | 优化目标平滑项及四点滤波 | 先测关节目标步长和实体跟随，再决定方案 |

最新输入覆盖解决历史位姿排队，单次求解及发布等待仍构成跟随延迟。
独立线程也仍受公共锁、同步日志和同进程 GIL 竞争影响。当前源码中的主要优化入口为：

| 入口 | 当前工作及可优化点 |
| --- | --- |
| `upper_body_teleop_execution.py: publish()` | 公共锁内执行反馈检查、补偿、消息构造、发布及同步日志；接收状态更新和 IK 提交需要同一把锁 |
| `upper_body_ros.py: receive()` | ROS 反馈回调在反馈锁内转换完整消息并同步写日志；与发布定时器共用单线程执行器 |
| `upper_body_diagnostics.py: record()` | 在日志锁内转换字段、JSON 序列化、写入并逐事件 flush |
| `upper_body_online_core.py: tcp_poses()/propose()` | 参考生成、上一目标比较、候选残差检查重复计算 FK，未使能侧也执行相关计算 |
| `upper_body_teleop_observe.py: live_frames()` | 等待选帧时每约 1 ms 查询接收器并检查反馈 |

以上为源码确认的执行路径，具体耗时和优化收益需按第 7 节测量。

## 7. 第一轮优化及实施顺序

第一轮目标为减少锁等待、重复计算和空转，保持当前运动目标及会话语义。
20 Hz 普通位姿、50 Hz 发布、完整帧、Grip 边沿、参考建立、补偿、故障锁存和退出契约沿用功能包说明。
沿用既有输入时限、反馈时限和发布间隔检查；本轮测量结果用于选择优化项，不增加阻断阈值。

### 步骤 1：建立当前版本基线并细分耗时

1. 先验证当前 20 Hz 版本，分别记录只读和执行模式下的单臂、双臂持续运动及快速松开／重按。
2. 复用输入序号、目标版本和已有日志事件，补充下表中的测量；测量字段在事件产生时固定。
3. `upper_body_teleop_stats.py` 输出分布和样本数，对比单臂、双臂及补偿开关条件。

| 测量 | 定义与用途 |
| --- | --- |
| 接收处理年龄、SDK 积压 | 原始回调接收至完整帧处理；识别接收侧阻塞 |
| 选帧年龄、普通选帧间隔 | 选中帧原始接收至交付、相邻普通位姿交付间隔；Grip 边沿单独统计 |
| 映射、IK、FK 耗时 | 分开计量参考生成、跟踪求解和残差检查；识别重复计算 |
| 公共锁、反馈锁和日志锁等待 | 申请锁至获得锁；识别线程互相等待 |
| 日志记录耗时 | 字段转换、序列化、写入及 flush；按事件类别区分 |
| 发布回调总耗时、发布间隔 | 包含补偿与日志，避免仅计发布前计算而漏掉回调尾部开销 |
| 目标年龄及来源 | 将发送时刻关联到目标接受时刻和该目标输入的原始接收时刻 |

当前 `input_age_s` 属于主线程已选帧，不能代替正在发送目标对应的输入年龄。
新增目标年龄关联字段应随不可变目标快照一起提交，避免从最新接收帧补写时间。
报告 P50/P95/P99/最大值及实际频率；源时间、本机接收、求解和发布时刻分别保留。
跨设备时间仅在时钟关系明确后用于端到端延迟。

### 步骤 2：缩短锁内工作并验证发布节拍

1. 发布侧在锁内取得一致目标及诊断快照，将诊断字段转换、JSON 序列化和写入移出公共锁。
   停止状态检查、发送及发送状态更新保持串行，确保停发后不会被旧计算恢复。
2. 反馈回调在反馈锁内完成解码、错误锁存及诊断快照固定，再在锁外转换和记录原始消息。
   日志保留回调接收时刻、对应序号和错误状态；异常继续传播。
3. 比较锁等待与回调总耗时。同步日志仍会占用所在 ROS 执行线程；若它继续主导发布延迟，进入第 9 节的异步日志方案。

补偿计算暂保留现有串行关系。只有步骤 1 确认其锁占用显著时，再设计锁外计算及发送前版本复核，
明确计算期间发生目标提交、Grip 变化或停发时的处理后实施。

### 步骤 3：缓存已接受目标的 FK

1. 在 `DualArmOnlineIK` 中按双侧已接受关节维护不可变 FK 缓存，初始化时建立。
2. `tcp_poses()`及上一目标比较复用同一版本缓存；新候选仍执行 FK 残差检查，并携带其对应 FK。
3. 缓存在候选成功提交时与关节、SEW、分支及目标版本一起更新；候选拒绝、失败或被边沿取代时保持原缓存。
4. 首次 Grip 的 HAL 参考、显式传入的其他关节目标使用对应 FK；缓存命中依据关节目标或版本，不能把旧 FK 用于新参考。
5. 对未使能侧及保持边沿复用已有计算，保留完整双侧诊断和现有结果字段。

该步骤复用计算，不改变 IK 种子、搜索窗口、分支选择、限位或残差判断。

### 步骤 4：以通知和周期等待替换 1 ms 轮询

1. 接收器增加条件通知；Grip 边沿、输入异常和会话结束唤醒主线程。
2. 普通位姿按下一次 50 ms 选帧时刻等待，醒来后只取最新完整帧；新普通帧不触发提前求解。
3. 超期后直接处理当前最新值，不补算已错过周期，不重复求解同一帧。
4. 执行模式继续由后台 ROS 线程处理反馈和发布；只读模式的等待必须兼顾 ROS 回调处理。
   等待上界由既有反馈时限和会话期限约束，不能无限等待输入通知而停止处理反馈。

### 步骤 5：容器对照验证并决定下一阶段

每步保留代码摘要及同类操作日志，完成第 8 节验收后再实施下一步。
本地执行语法、静态检查和代码审阅；用户按根目录流程同步，在机器人 Humble 容器构建和运行回归用例。
不依赖机器人的日志读回和离线分析可在本地执行。
第一轮完成条件为：现有会话与发布契约通过验证，新增测量可读回，每项优化有同条件前后对比。
性能是否改善由测量报告说明；没有改善的修改不以“已拆线程”或“已缓存”认定有效。

## 8. 验收操作与预期结果

| 操作 | 预期结果 |
| --- | --- |
| 持续单臂及双臂更新输入 | 普通位姿按最新完整帧推进，历史待解位姿不增长；普通选帧不超过 20 Hz，边沿单列 |
| 求解期间快速松开并重按 Grip | `released`、`reference_established`保序；跨边沿普通候选记录`ik_superseded`，不推进已接受状态 |
| 对照首次 Grip、重按及另一侧首次 Grip | HAL／已接受理想目标的参考来源符合功能包约定，未接管侧目标保持 |
| 缓存前后使用同一快照和选中输入序列离线比较 | 接受／拒绝结论、关节、SEW和分支一致，报告残差差值；失败与丢弃不推进缓存版本 |
| 在等待选帧期间触发输入失联、源时间停滞或反馈失效 | 原有错误被传播，执行侧按既有契约停发；等待不会掩盖异常 |
| IK 耗时增加且接收线程仍持续更新 | 主线程处理超时仍可独立停发，接收更新不会刷新旧处理时间 |
| 执行期间记录目标提交和实际发布时刻 | 每条命令可追溯到完整已接受目标；核对 50 Hz 目标节拍及既有 80 ms 发布间隔检查 |
| 优化锁和日志后重复同类操作 | 原始反馈、错误及时间字段保留，日志可完整读回；对比锁等待、回调耗时和发布间隔分布 |
| 正常结束、Ctrl-C及错误退出 | 停发、接收线程结束、SDK关闭及日志收尾顺序符合功能包约定，无遗留工作线程 |

离线计算一致性与现场调度性能分别验收。现场选帧会受运行节拍影响，不能要求不同版本每次现场选中的输入序号完全相同。

| 独立日志写入线程 | 移出公共锁后，日志转换／写入仍明显影响接收年龄或 ROS 发布间隔 | 生产者固定事件时间、顺序及不可变内容，写入线程完整保存；确定序列化归属、排队策略、未落盘窗口、写失败传播和退出排空，保留原始反馈及错误记录 |
| 输入或 IK 进程隔离 | 日志与锁优化后，IK繁忙仍伴随接收或发布延迟，测量支持同进程竞争是主要因素 | 选择隔离输入还是 IK；传递完整帧、Grip边沿、目标版本及异常，明确进程退出与重启关系，再评估收益 |
| 输出插值或滤波 | 最新位姿调度稳定后，关节目标步长与实体记录显示台阶或抖动影响操作 | 比较插值与滤波的平顺性、延迟和跟踪误差；确定参数、Grip参考／停发行为及补偿与理想目标的关系 |
| 提高普通位姿求解频率 | 双臂实测计算与日志开销有余量，20 Hz 更新成为主要跟随延迟来源 | 将频率改为显式参数，依据双臂耗时分布选择，继续超期不补算；不直接采用宇树默认值 |

若四点滤波按“最新至最旧”使用`[0.4, 0.3, 0.2, 0.1]`，对匀速信号的加权滞后为一个采样周期，
在 20 Hz 下约 50 ms。平滑效果必须与新增延迟一起评估。
当前种子取上一已接受理想目标，补偿仅作用于发送侧；改用实际关节作为种子会改变该关系，须另行设计验证。
宇树的 250 Hz、电机增益、前馈力矩和按实际反馈裁剪位置不作为当前 X2 原生上肢接口的实施参数。
