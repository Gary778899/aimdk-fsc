# 第二步：包边界评审与采集器调整目标

更新日期：2026-10-23。本文依据当前官方 SDK、自研包源码及用户确认的范围更新。本轮只进行需求与结构设计，不修改程序、launch、依赖声明或同步配置，不执行机器人容器构建与测试。

## 1. 当前决策与下一步目标

**下一步以官方原始话题清单为依据，调整 `data_collection_edge_agent`，使其能直接录制机器人原始反馈与实际发布的命令，不再依赖 `locomotion_wrapper` 提供标准状态。** 功能需求、候选话题、数据语义和模块结构见 [原始话题采集器设计](raw_topic_recorder_design.md)。

本轮范围作以下调整：

1. `locomotion_wrapper` 原本服务于 ONNX 模型的下半身控制研发链路，该方向目前不需要。保留现有包，相关 profile、时钟检查、诊断和内部结构调整均后置，不作为采集器开发前置条件。当前复制版本本身仍为只读观测代码，并不等于包含完整模型控制功能。
2. `src/test/` 下的头部、手臂脚本服务于前期验证，保持现有入口与逻辑。本阶段取消此前关于 `common/`、日志、时效监视、插值、端点判定及服务等待的公共能力抽取计划。
3. 不优先新建 `aimdk_bringup`，不以整理联合启动代替原始话题采集能力。采集器保留一个独立启动入口；旧联合入口在实现阶段取消默认启动观测包的行为，并说明兼容／停用方式。
4. 保留官方包、自研包的现有平铺结构；不为目录形式进行搬迁。正常依赖官方消息定义、ROS 库与第三方库，不依赖其他自研业务包。

## 2. 包边界与当前状态

当前 `src/` 一级 manifest 包名共 9 个，未发现一级包重名；该结论来自本地静态扫描，不等同于容器包发现结果。

| 包／目录 | 归属与职责 | 本阶段处理 |
| --- | --- | --- |
| `aimdk_msgs` | 官方 SDK 消息与服务定义 | 原始采集的接口依据，不加入实验业务消息 |
| `ruckig` | SDK 携带的第三方轨迹库 | 保持现状，不是采集器必需依赖 |
| `examples`、`py_examples` | 官方示例和接口使用参考 | 保持现状，不作为自研公共库 |
| `robotop` | 用户确认未修改的官方诊断工具 | 保持现状，不承载采集与实验管理 |
| `aimdk_test`（`src/test`） | 前期头部、手臂验证工具 | 保留脚本及内部依赖，不提取公共能力，不调整控制行为 |
| `aimdk_functions`（`src/functions`） | 自研功能命令，目前为音量／静音 | 保持现状，不作为采集依赖 |
| `data_collection_edge_agent` | 独立原始话题采集器 | 下一步开发重点：配置、订阅、MCAP、会话状态与数据完整性 |
| `locomotion_wrapper` | 下半身模型链路中的只读观测／消息转换环节 | 保留并后置，采集器不要求它构建、启动或发布数据 |
| `tools/`（按需新增） | 采集控制客户端、录包检查及离线分析 | 最小控制／检查工具随采集实现补齐；复杂分析后续开展 |

目标数据链路：

```text
机器人官方话题 ──→ data_collection_edge_agent ──→ MCAP + 会话记录
         │
         └──→ locomotion_wrapper ──→ 标准状态／后续模型链路（暂不开展）
```

采集器需要官方话题有实际发布者，但不负责启动机器人原生服务或任何自研转换节点。启动成功、发布者存在、收到消息和数据完整是不同状态，必须分别说明。

## 3. 当前采集器与目标之间的差距

| 当前事实 | 目标调整 |
| --- | --- |
| 只支持标准 `JointState` 和 `Imu` | 增加官方 `JointStateArray`、`HandStateArray`、`McCommonState`、`UpperBodyCommandArray`、`HandCommandArray` 的类型支持，原始 IMU 直接使用 `sensor_msgs/msg/Imu` |
| 默认录 `/humanoid/joint_states`、`/humanoid/imu` | 首版默认使用经 SDK 核对的上肢原始话题 profile；标准化话题不再是启动前提 |
| [manifest](../src/data_collection_edge_agent/package.xml) 依赖观测包，[联合 launch](../src/data_collection_edge_agent/launch/robot_data_collection.launch.py) 无条件启动它 | 实现阶段移除观测包依赖，并同步处理旧入口，不能只删 manifest 却保留必需的联合启动逻辑 |
| 话题和类型配置固定为两路 | 基于类型白名单配置多话题及逐话题 QoS、必需性与缺流告警参数 |
| 回调持锁直接写盘，缺少会话数据质量统计 | 分离接收和写入，采用有界队列；明确溢出、停止排空和错误行为，提供已接收／已写入／已丢弃计数 |
| `START` 的 ACK 只确认 writer 初始化 | 保留这一语义，新增状态查询与会话摘要，不把 ACK 解释为所有必需话题已收到 |
| README 引用缺失的旧 Humble 指南、控制／导出工具 | 实现时按独立原始采集流程更新，不恢复旧回迁路线；未提供的功能明确标为未实现 |
| CMake 要求 `zmq.hpp`，manifest 未声明 `cppzmq-dev` | 实现阶段补齐系统开发依赖，并按机器人 Humble 环境核对消息与 rosbag2 支持 |

官方清单中的服务名称不是普通数据话题；首版不轮询运动服务，也不将服务名称直接加入录制配置。`GetMcAction` 的应答不能用 `McCommonState` 话题录制来冒充；本阶段以话题状态记录为范围。

## 4. 本阶段不再推进的工作

- 不重构 `aimdk_test`，不创建 `aimdk_common`，不从测试脚本抽取运动模式、轨迹或退出策略。
- 不新增观测包上肢 profile，不修订其关节排序、时钟推进、可选组缓存和结构化诊断实现；原评审发现继续作为该包未来恢复开发时的检查项。
- 不接入 ONNX，不开展下半身控制、影子推理或策略部署。
- 不把数据清洗、标准状态聚合、控制正确性判定放进原始采集器。源消息包含错误、非有限值或异常时间时也应留存，质量检查仅作旁路标记。
- 不先开发图形界面、视觉大流量记录或复杂实验组合框架。

## 6. 后续顺序与完成条件

1. **当前交付：设计。** 核对官方话题与消息，明确 [首版采集器需求和范围](raw_topic_recorder_design.md)，取消不再需要的重构前置项。
2. **下一步：按设计实现采集器。** 完成类型与配置扩展、独立启动、会话管理、数据写入和最小控制／检查工具；不修改控制脚本或观测包。
3. **由用户在机器人容器核实。** 核对话题实际类型、发布者 QoS、数据率和时间基准；构建及验证独立 START／STOP、缺流、错误和 MCAP 读回。不运行运动控制作为采集器构建验收的一部分。
4. **进入任务 3 的实验闭环。** 基于已可用录包完成离线检查、目标／反馈分析与夹爪验证，模型控制与观测包改造继续后置。

任务 2 完成条件调整为：代码与数据边界明确，原始采集器不依赖其他自研业务节点，容器内具备可核实的独立采集与读回证据。公共能力抽取、观测包改造和新建组合包不再作为本阶段完成条件。当前需求设计已形成，程序尚未按新设计实现或验收。
