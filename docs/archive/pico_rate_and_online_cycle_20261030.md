# PICO输入频率核对与在线周期验证方法

日期：2026-10-30。范围为选定的XRoboToolkit链路和本项目下一阶段调度设计。
本次查阅上游main公开源码和本地SDK文档，未连接PICO、运行基准或执行机器人测试。
公开源码不能证明现场安装APK/PC Service版本的实际帧率，接入时记录版本并实测。

## 频率查证

上游[Unity TcpHandler.cs](https://github.com/XR-Robotics/XRoboToolkit-Unity-Client/blob/main/Assets/Scripts/Network/TcpHandler.cs)
在Update中收集跟踪数据；待发队列少于2条时入队，发送线程取出并发送，同时更新界面FPS。
该路径没有固定20ms生成周期。因此没有依据把PICO数据发送率直接写成固定50Hz。
实际生成、发送、PC接收和机器人目标帧率分别受应用运行与链路影响。

[TrackingData.cs](https://github.com/XR-Robotics/XRoboToolkit-Unity-Client/blob/main/Assets/Scripts/TrackingData.cs)
在构造数据时写入timeStampNs；
[Utils.cs](https://github.com/XR-Robotics/XRoboToolkit-Unity-Client/blob/main/Assets/Scripts/Utils.cs)
由UTC毫秒生成该字段，名称中的ns不代表硬件纳秒采样精度。

[Python绑定](https://github.com/XR-Robotics/XRoboToolkit-PC-Service-Pybind/blob/main/bindings/py_bindings.cpp)
在SDK回调中覆盖最新左右位姿和时间戳，getter返回这些缓存，各字段分别加锁。
因此轮询次数不等于新数据帧数；快速轮询可重复读同一帧，慢轮询可错过已被覆盖的帧。
现有分字段getter也不保证左右位姿与时间戳同属一帧。
为满足每帧目标有IK结果的要求，输入适配应提供同一回调内的完整快照、接收序号及本机单调接收时间，
并区分源包、缓存读取、适配采样和已提交控制器的目标帧。

### 输入频率实测

先只读接入，保持与后续遥操一致的设备、网络和功能配置，采集静止、缓慢移动、双手移动三类片段。
建议每类1～3分钟，并补一次较长会话观察网络波动；时长是采样方案，不新增执行门槛。

在PC接收回调和机器人目标接收处分别记录单调时间、接收序号、源时间、完整双侧位姿及有效性。
计算有效新帧率(N−1)/(t_last−t_first)、接收间隔中位值/P95/P99/最大值、重复源时间、
源时间回退、适配采样或丢弃计数。初查可统计getter返回的不同时间戳数量，
但不能由此证明所有源包均被捕获；不要按位置是否变化判断新帧。
跨设备源时间与接收时间未校准时，不直接相减宣称端到端延迟。

## 输入、IK、补偿、发布分别定频

本地SDK原生上肢文档推荐50Hz发送；当前执行器也采用20ms定时器。
先保留该节奏，不因PICO低频而自动降低命令发送频率。

每个新的控制器目标帧求解一次双侧IK。无新目标时复用最后已接受的理想关节目标，
不为重复读取的同一输入重复IK；新鲜度与断链处理仍有效，重发不能掩盖输入停止。
补偿依赖理想关节及当前IMU/腰反馈，首轮仍按50Hz发布周期使用有效输入计算，
不能仅因PICO低频就认为补偿输入也不变。独立降低补偿刷新频率需用观测结果另行评价。

| 实测新目标频率示例 | IK平均到达间隔 | 首轮命令/补偿节奏 |
| --- | --- | --- |
| 25Hz | 40ms | 50Hz / 50Hz |
| 30Hz | 约33.3ms | 50Hz / 50Hz |
| 50Hz | 20ms | 50Hz / 50Hz |

表中间隔不是允许全部用满的耗时预算：还需计入到达抖动、排队与发布调度。
若输入更高频，明确适配采样率及原始序号映射；已经提交控制器的每帧必须记录求解结果或失败。
关节插值若加入，则明确其发生在IK之后；每20ms插值一个新TCP目标再做IK，仍然要求50Hz求解。

低频IK与高频发布需要调度隔离：若一次33ms求解仍阻塞同线程20ms定时器，降低IK频率不能保证发布周期。
是否需要独立执行上下文以实际阻塞和积压测量决定，不预先堆叠线程架构。

## 机器人容器内的验证步骤

基准入口尚未实现。实现时复用gripper TCP、实际双侧状态提交、补偿、消息组装、反馈与诊断路径，
采用同一单调时钟记录各阶段；本地单侧回放耗时不替代此项验证。

1. 用已保存的真实关节/IMU/腰快照与平移、旋转、组合目标，运行双侧逐帧求解及补偿；先不向机器人命令话题发布。
2. 加入实时反馈订阅、正式日志配置和完整消息组装，在隔离的基准话题发布并由独立订阅端统计接收。
   同时测20ms发布与实测输入帧率的IK，验证完整调度而非只计函数耗时。
3. 用真实PICO目标重做该项，保留帧序号、输入到首次发送的等待、队列与过期情况。
4. 通过只读审阅后由操作者按项目流程验证受限范围真机持续会话，核对实际命令发送及反馈；不得将隔离话题结果表述为实体控制验收。

建议对正式配置连续记录至少数分钟，分别覆盖双侧平移/旋转/组合、补偿开/关以及实际启用的数据记录/视频负载。
模型加载、首次IK和周期稳态分别报告，不将初始化时间混入或悄悄剔除稳态超时。

### 每帧/周期记录字段

- 输入：input_seq、源时间、本机接收时间、目标可用时间、求解开始及结束。
- 计算：左右IK、候选校验、补偿、消息组装、日志耗时，接受/失败及最后提交序号。
- 发布：计划唤醒时间、实际开始时间、publish调用前后时间、command_seq、关联input_seq。
- 订阅端：同一主机单调接收时间、command_seq、缺失/重复及接收间隔。

完整处理时间从进入本周期处理到该周期必要工作结束，包含正式日志开销；
发布调度延迟为实际开始减计划开始，发布间隔由相邻实际发送时间计算。
input_seq到首次command_seq的关联用于计算输入等待与目标复用次数。
publish返回只说明本进程完成调用，不证明MC内部接收或生效；隔离订阅端只补充DDS传输证据。

### 判断方式

报告各指标P50/P95/P99/最大值，额外列出超过20ms的处理周期数、发布截止时刻超期数、
最长连续超期及队列等待随时间变化。只有平均值低于20ms，不能认定50Hz稳定。
若声称观测窗口内每次处理均在20ms内完成，需该窗口超期计数为零；
存在超期时量化其次数和影响，由实验要求决定是否接受，不隐藏为均值。
处理时间低于20ms仍需检查定时器迟到、实际发送间隔和接收间隔；普通Linux运行结果是观测证据，不是硬实时保证。

若采用低于50Hz的新目标IK，则按实际输入节奏评价IK完成、等待和积压；
20ms要求保留给发布侧的补偿、校验、消息及必要日志调度，不再要求每个发布周期都重新IK。
