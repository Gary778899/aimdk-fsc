# X2 Ultra 头部单关节分步验收

适用用户已确认的原旗舰 X2 Ultra、固件 1.1.5 / SDK 1.1.0、夹爪配置。当前只实现 yaw 首测，不实现手臂运动。原旗舰仅 yaw 有效，pitch 不开放测试；两槽消息不代表两项有效自由度。用户已在机器人容器完成两次头部执行：一次反馈/时钟联合检查中止并确认交回站立，一次端点验收通过；两次均观察到运动前后身体抖动。新增诊断版本尚未完成容器验证，端点通过不代表身体交接平滑已经通过。

## 开发与验证

本地只编写代码和进行静态检查。先使用 `.vscode/tasks.json` 的“机器人：预览同步”和“机器人：推送工作区”，再进入机器人开发板的实际开发容器，在确认的项目路径内构建和测试：

```bash
# 在机器人开发板容器内，加载 Humble 和 SDK 环境后执行
python3 -m colcon build --base-paths src --packages-select py_examples
source install/local_setup.bash
python3 -m pytest -q src/py_examples/test/test_head_test.py src/py_examples/test/test_head_test_adapter.py
```

若缺少 pytest 或 aimdk_msgs，不能将未执行或跳过的测试计为通过。当前修改尚未完成机器人容器内构建和测试；历史本地验证不代表容器验证。

## B 阶段：只读联合验收

连接用户已验证的网线 / ROS 网络。先由操作者确认原生运控已稳定站立，周围空间合适，且无其他程序控制头部。执行：

```bash
ros2 run py_examples head_test
```

默认仅订阅反馈、调用 GetMcAction；不创建运动发布器或 SetMcAction 客户端。输出 GetMcAction 模式、RUNNING 状态、MC body 原始数值、头部角度和检查结果；明确提示不检查 FSM。要求现有模式 STAND_DEFAULT，不自动从被动、躺姿或行走切入站立。

反馈：`/aima/hal/joint/head/state`；MC 状态：`/aima/mc/common/state`，均 BEST_EFFORT + TRANSIENT_LOCAL。按名称匹配 yaw/pitch，拒绝重复、yaw缺失、错误状态和非有限值。原旗舰反馈如不含无效 pitch，协议第二槽填 0；如含 pitch 则保持其实测值。此规则只适用本工具固定的原旗舰型号。

启动条件参考 get_mc_action：GetMcAction 查询成功，`action_desc=STAND_DEFAULT` 且 `status.value=RUNNING(100)`。MC body 仍须报告 `MC_BODY_POSE_STAND`。按用户要求不再检查 FSM，也不解释 raw=4 是否稳定。进入 HEAD_ONLY 后检查该模式持续 RUNNING；结束时确认 STAND_DEFAULT / RUNNING。默认命令仍只读，运动须显式加 `--execute`。

头部反馈本机接收年龄、源时间推进和 ROS 时钟推进均限 200 ms；源时间相对本机 ROS 时间为 -50..200 ms。MC状态限300 ms，源时间不能倒退或冻结。要求真机与本机时钟同步；发现时差先纠正时钟。零或无效反馈戳不被改写或当成新鲜数据。

请把完整终端输出交给主代理共同验收，只读通过后再启动运动。

## C 阶段：由用户明确启动头部运动

```bash
ros2 run py_examples head_test --execute
```

默认 yaw 正向 3°，3秒出程、3秒返程，一次往返。可用 `--amplitude-deg -3` 测反向；幅度绝对值范围1..5°（下限确保0.5°到位容差不能把完全未运动判为通过）、单程3..10秒，轨迹峰值速度不超过5°/s。yaw软件范围±19°（机型表±20°留1°边界），起点或终点超界即拒绝。pitch保留值需在 SDK 示例范围±0.3838rad内；该值不是原旗舰pitch可动能力的声明。

流程：查询确认现有默认站立（不再重复发送站立请求）→请求并确认 HEAD_ONLY→等待确认后源时间与接收时间均更新的反馈建立起点→精确发送起点并验证新反馈→50Hz五次平滑曲线出程→端点实测到位→返程→实测到位→请求并确认默认站立。

指令 `/mc/upper_body_command` 使用 BEST_EFFORT + VOLATILE。每次发送两个头部槽；手部子模式0、空手部目标，14个arm槽按原头部例程填零，仅在确认 HEAD_ONLY 时发布。不能将这个编码复用到双臂模式。指令时间戳明确为0，按上肢专门文档由运控使用接收时刻；反馈时间戳仍完整检查。

运动中模式异步查询，不阻塞50Hz发布；模式状态过期400ms、请求超时300ms、反馈失效、站立状态失效、调度超期或跟踪误差超过5°即停止。出程和返程均要求端点误差≤0.5°保持300ms，最多等待2秒；消息发完不算通过。

## 身体抖动诊断日志

默认自动定位项目根目录，创建 `log/head_test_<UTC时间>_<唯一标识>.jsonl`；启动时打印绝对路径。从其他目录运行且无法定位项目时，用 `--log-dir /实际项目路径/log` 指定。每次运行独立文件，不覆盖旧日志。

日志记录 UTC 时间（`wall_time_ns`）、单调时间和相对启动秒数，包含模式切换请求/响应/确认、MC 状态变化、起点捕获、首帧与每帧发布（序号、目标及发布间隔）、出程/返程端点确认、最后发布时刻与交接间隙、异常发生时的状态以及恢复结果。反馈快照约 10 Hz，事件同时附带最近头部位置、反馈源/接收年龄、时间冻结时长与模式确认年龄。`fsm_raw` 仅记录，不参与放行。

接收超时、源时间戳冻结、ROS 时钟冻结分别报告具体年龄与 200 ms 限值；MC 状态和模式超时也显示年龄。ROS 时间在服务等待及运动循环中独立观察，保留倒退和时效检查，不放宽阈值。

为减少运动循环磁盘写入，事件先存内存，正常完成、受控失败或 Ctrl-C 后写盘。最多保留最近 20000 条，`log_close.dropped_events` 标明截断数量。进程被强制杀死或断电时缓存可能丢失。日志只用于对照交接时序，没有身体 IMU 或腿部测量，不能单凭它确认抖动原因。

同步并在机器人容器构建、运行测试后执行；不需要额外开启日志参数：

```bash
ros2 run py_examples head_test --execute
```

## 异常与待真机核定事项

- 正常与异常模式切换均使用有界服务等待/响应等待，不重试发送同一运动请求。`--timeout` 为单次等待1..10秒，默认5秒；一次流程可能包含多次等待。
- 正常最后端点验证后停止发送头部指令，再请求/确认默认站立；此交接存在服务往返间隙。HEAD_ONLY退出/断流保持行为、模式接管前默认目标行为未在材料中保证，须向厂家或真机受控验收核定，不能声称全程无目标间隙。
- 异常和 Ctrl-C 不执行盲目返程。只有重新查询仍为 HEAD_ONLY 且当前反馈/站立检查有效，才尝试有界交接默认站立。模式已变更不抢回，通信失效或错误锁存时不切模式；控制器可能仍保留 HEAD_ONLY，需操作者检查和接管。
- HEAD请求已到达但本机确认失败时，远端完成状态未知，仍尝试上述新查询排查。停止发布、脚本退出、网线中断均不保证机器人保持或恢复安全站立。
- 不故意拔线或制造失联来验收；不自动调用阻尼、零力矩或急停接口。实物停止措施由现场操作者掌握。
- 下半身平衡由原生运控负责；GetMcAction 模式、RUNNING 和 body=STAND 为软件门槛，不能替代现场观察。首帧接管连续性、正常/异常交接、头部指令实际接受情况均须逐步验收。

头部验收通过后，再开发单臂单关节执行；夹爪保持编码仍需独立核实。
