## 结论

1. 首次执行已成功进入 `UPPERBODY_REMOTE_SPLIT / RUNNING`（URS），随后右肘位置反馈相对切换前偏移 **+0.505352°**，超过软件的 0.5°保护阈值，因此中止。不是进入 URS 被拒绝，也不是左腕走完 2°后失败。
2. 自动交接存在明确的检查复用问题：恢复过程等待 GetMcAction 时再次执行运动阶段的漂移检查，同一个右肘偏移立即抛出异常，**尚未发送返回 STAND_DEFAULT 的 Set 请求**。
3. 下一次运行读到 `body=1 / URS / status=100`，与启动要求的 STAND_DEFAULT 不符，所以在基线阶段拒绝继续。它是前次未完成交接的后续表现，不是新的 body 非站立错误。
4. 双臂为何在接管后偏移，现有日志不能唯一确定。切换连续性、URS 初始目标、首帧接收及控制器保持行为需要进一步证据；不能据此认定硬件故障、消息顺序错误或指令已被固件接受。

## 自动交接为何没有发生

代码调用链为：

`abort_handoff → mode → call → tick → 右肘漂移检查再次失败`

[abort_handoff](../src/py_examples/py_examples/arm_test_motion.py) 设置允许模式为 URS/STAND 后先查询当前模式，但没有切换到独立的恢复检查策略。`call()` 等待服务回复期间继续调用 `tick()`，后者仍执行运动阶段的累计漂移检查。日志第 116 行有 Get 发送，第 117 行直接出现同一错误，既无该查询的处理结果，也无第二个 `transition_begin` 或返回站立的 Set。

所以终端的 “Automatic handoff unconfirmed” 在本次具体意味着：**恢复流程在发送返回站立请求之前中断**，不能解释为固件拒绝了返回站立。

现有漂移异常测试只要求不再发布、不执行返程，没有要求在反馈有效且归属仍确认的情况下发出站立交接。Ctrl+C 交接测试中的反馈也没有持续漂移，未覆盖本次故障组合。以上为测试源码审阅结论，本次未运行测试。

## 后续处理建议

1. 优先修复恢复检查的职责划分：中止后保持停发，不做返程；在反馈有效、body 仍站立、无硬件故障且新查询确认 URS 归属时，允许有界尝试一次站立交接。已经触发的轨迹偏移应保留为失败原因，避免它使恢复查询必然失败；反馈失效、故障和外部接管仍需阻止自动接管。补充持续漂移情况下恢复流程的断言。
2. 在继续腕部轨迹前调查 URS 接管及 q0 保持：现有首帧验证约 1.2 ms 后就开始出程计算，只要求较新的 arm/hand 反馈，不能证明控制器已经接收首帧并稳定保持。需要明确固件在 URS 首帧前的目标和接管方式，并记录匹配订阅者、固件接收/目标信息（若可提供）。本次 2 帧不足以评价稳定跟踪能力。
3. 若后续增加独立保持诊断，应保留完整 14 关节 q0 和实测夹爪位置，并继续检查非测试关节。不要通过扩大阈值、改关节顺序、裁剪起点或把另一只手臂填零来消除报错。URS 接口本身是双臂完整目标，单臂测试也依赖另一只手臂保持。
4. 下一次启动前由现场操作员恢复并确认 STAND_DEFAULT / RUNNING，再重新采集只读基线。再次运行时双肘相对原基线已偏移约 2.15°/2.41°，即便仅恢复模式也不能假定姿态已满足参考窗口；需重新读取确认。不要只反复启动 `--execute`。

本次未修改控制实现。软件中止及恢复失败的因果链已确定；真实控制器接管偏移的底层原因仍待固件侧或更细的接收/目标证据确认。
