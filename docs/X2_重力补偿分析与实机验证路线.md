**X2 重力补偿分析、实机定位方法与开发路线**

整理日期：2026-10-24。适用项目：当前 `x2_simulation` 交付目录。目标：评估并实现“下半身稳定站立，上半身进行位置控制并获得重力补偿”，最终在真机验证。

本文区分三类依据：项目文件和二进制的静态检查、已完成的离线仿真实验、用户提供的现场验证。本文不表示已经完成真机动力学辨识或真机补偿测试。

**一、已确认的结论与实机补充信息**

| 项目 | 当前结论 | 依据 |
| --- | --- | --- |
| 真机 URS 模式 | **存在，且用户已验证可对上半身关节及夹爪进行位置控制** | 用户实机验证；URS 对应 `UPPERBODY_REMOTE_SPLIT` |
| 真机 URS 是否自带重力补偿 | **待确认** | 位置控制有效，不能单独证明补偿存在或不存在 |
| 当前仿真 MC 的 URS 模式 | **不支持** | 用户调用返回 `can not find action: UPPERBODY_REMOTE_SPLIT` |
| 当前仿真的上半身话题 | 查询时 `/mc/upper_body_command` 不存在 | 用户执行 `ros2 topic info` 返回 Unknown topic；静态检查也没有找到对应 MC 接收实现 |
| 当前仿真 MC 的动力学补偿 | VR 控制器配置和动态库中有明确实现线索 | 补偿配置、函数调用及结果缩放指令 |
| 该 VR 补偿在运行时是否生效 | **尚未验证** | 目前没有运行中的补偿输出及对照实验；不能把初始化成功当作启用证据 |
| 双臂模型是否适合开发原型 | 可以开展标称模型上的重力矩计算、固定躯干补偿实验 | 模型参数完整，已完成离线验证 |
| 当前交付包能否直接复现实机 URS 下的站立上肢控制 | **不能直接复现** | 仿真 MC 缺少实机已具备的模式及接收链路 |

当前缺口主要是仿真 MC 的控制接口与控制权分配，而不是 MuJoCo 无法模拟重力补偿。若补齐上肢控制接入、下肢平衡协同和模型参数，仍可继续开发；但自行搭建的控制路径不能直接代表真机 URS 的内部实现。

**二、当前仿真 MC 中定位到的补偿信息**

**2.1 配置位置与含义**

配置文件：[joint_controller_config.yaml](../mc/bin/mc_param/src/robot/lx2501_3_t2d5/remote_controller_config/joint_controller_config.yaml)。

```yaml
jointControllerParam:
  # 是否打开补偿: 0:不补偿 1：根据实际角度补偿 2：根据目标力矩补偿
  compense_switch: 1
  # 补偿系数：
  compense_ratio: 0.8
```

按注释，当前选择根据实际状态进行补偿，补偿结果乘以 0.8。假设某关节计算得到补偿力矩 10 N·m，缩放后为 8 N·m。它缩放的是补偿项，不是修改机器人质量，也不是把电机总输出限制为 80%。位置、速度反馈还可能提供其他力矩。

模式 2 的“根据目标力矩补偿”注释较含糊，不能仅靠注释还原算法。也没有资料说明为何采用 0.8，不能据此认定它是最优比例或真机通用值。

[operation_config.yaml](../mc/bin/mc_param/src/robot/lx2501_3_t2d5/remote_controller_config/operation_config.yaml)还定义：

```yaml
basicConfig:
  # 0:遥操作模式 1：关节单独测试模式 2：replay 3:力矩补偿状态
  running_mode: 0
```

这里的 `running_mode` 是 VR 控制器内部配置，不等于 MC 的全局动作模式。不能仅把它改成 3，就认定已经获得可在站立真机上使用的拖动或补偿接口。

`sim/remote_controller_config` 是指向 `../remote_controller_config` 的符号链接。但配置文件存在仍不证明运行进程加载了它；要结合实际启动路径、机器人型号和配置解析结果判断。

**2.2 动态库中的计算路径**

交付库为 `mc/lib/libmc_runner_vr_remote_controller.so`。对其符号和局部反汇编的检查确认了：

```text
JointController::jointContorllUpdate(...)
    → JointController::compenseBodyInertia()
    → pinocchio::rnea(model, data, q, v, a)
    → 计算结果逐元素乘以补偿系数
    → 保存至内部力矩向量，供 updateJointsCommand(...) 输出
```

其中 `jointContorllUpdate`、`compenseBodyInertia` 的拼写沿用二进制符号，不是本次重新命名。检查不仅发现了名称，还发现实际调用及结果缩放指令。

`rnea` 是递归牛顿欧拉**逆动力学**，用于由姿态、速度和加速度计算力矩；它与求目标关节角的“逆运动学”不同。固定基座、忽略摩擦和外部接触时，可以表达为：

```text
tau_ID = M(q) * qddot + C(q, qdot) * qdot + g(q)
```

当速度和加速度都取零时，`rnea(q, 0, 0) = g(q)`，得到平衡重力所需的力矩。非零速度或加速度输入会引入运动相关项。接口定义参见 [Pinocchio 官方文档](https://gepettoweb.laas.fr/doc/stack-of-tasks/pinocchio/master/doxygen-html/rnea_8hpp_source.html)。

目前仍需确认这条路径实际使用的 URDF、输入向量内容、躯干姿态处理、关节映射及运行状态。库中含 `/x2.urdf` 字符串，但字符串本身不足以证明最终加载路径。因此，已确认的是“存在动力学补偿实现”，尚不能把它直接认定为正在生效的纯重力补偿。

**2.3 VR 模式、URS 与上半身话题的关系**

当前 [MC 配置](../mc/bin/mc_param/src/robot/lx2501_3_t2d5/mc_sim.yaml)明确订阅：

```text
/aima/teleop_bridge/vr_data
    → VR 数据接收
    → VR_REMOTE_CONTROLLER 对应的控制分支
```

[action_setting.yaml](../mc/bin/mc_param/src/robot/lx2501_3_t2d5/action_setting.yaml)将 `vr_remote_controller` 配置在 `VR_REMOTE_CONTROLLER` 动作中，周期为 2 ms。[McAction.msg](../aimdk/src/aimdk_msgs/interface/robot/mc/action/McAction.msg)定义了 `VR_REMOTE_CONTROLLER=400`，只是当前 `set_mc_action` 示例菜单没有列出它。

SDK 的 [upper_body_control.py](../aimdk/src/py_examples/py_examples/upper_body_control.py)则以 50 Hz 发布 `/mc/upper_body_command`，消息为 [UpperBodyCommandArray](../aimdk/src/aimdk_msgs/interface/robot/mc/openapi/msg/UpperBodyCommandArray.msg)，包括 `head_pos`、`arm_pos`、`hand_pos`。示例本身不加载动力学模型、不调用 RNEA，也不计算补偿力矩。其 `joint` 选项是灵巧手手指关节控制，现有各预设的双臂 `arm_pos` 均为零；`hand_sub_mode` 不是补偿开关。

目标位置接口完全可能由下游 MC 自动补偿，不能因其消息没有 effort 就判定真机没有补偿。但当前仿真 MC 的原始及生成配置中没有找到 `UPPERBODY_REMOTE_SPLIT`、`HEAD_ONLY` 或该话题接收配置；扫描交付 MC 动态库及主程序，也没有找到对应话题、消息和模式名称。用户随后提供了运行结果：

```text
ros2 topic info /mc/upper_body_command --verbose
Unknown topic '/mc/upper_body_command'

ros2 run py_examples set_mc_action URS
Failed (code=-1): can not find action: UPPERBODY_REMOTE_SPLIT
```

Unknown topic 单独只能说明查询当时没有发现该话题；结合动作切换失败及静态检查，已能确认当前交付仿真不能直接使用这条 URS 控制路径。**这个结论仅针对当前仿真 MC，不适用于用户已经验证有 URS 的真机 MC。**

用户另一次查询为 `PASSIVE_DEFAULT`、`Mode status: 100`。按 [McActionStatus.msg](../aimdk/src/aimdk_msgs/interface/robot/mc/action/McActionStatus.msg)，100 表示 RUNNING，即被动模式运行中；按当前动作配置，此时没有运行前述 VR 控制器。

**三、模型条件及已完成的离线实验**

实际仿真入口是 `sim_mujoco/.../model_info/scene.xml`，包含 [x2.xml](../sim_mujoco/configuration/robot/lx2501_3_t2d5/model_info/x2.xml)。使用交付动态库加载成功，实际 MuJoCo 版本为 3.3.7、步长 1 ms、重力 `(0, 0, -9.81) m/s²`。

| 项目 | 审计结果 | 限制 |
| --- | --- | --- |
| 双臂动力学参数 | 每侧 7 个 link 均有质量、局部重心、惯性；左臂 3.940932 kg，右臂 3.930909 kg | 未找到对应具体真机的实测辨识记录 |
| 与参考 URDF 的臂部一致性 | 与 `mc/bin/mc_param/src/urdf/x2_31dof_hand.urdf` 的质量、局部重心一致，惯性张量仅有导出精度差异 | 不代表 MC 中每个控制器都使用该 URDF |
| 全身质量 | MuJoCo 43.474797 kg；参考 URDF 显式质量合计 41.627972 kg | 差异约 4.44%，几乎都来自骨盆 |
| 骨盆参数 | MJCF 无显式 inertial，编译后质量由几何推算为 5.031811 kg；参考 URDF 为 3.184938 kg | 影响全身动力学与站立验证 |
| 末端配置 | 臂部终止于 wrist_roll，无独立的持物负载 body | 腕末端质量可能含部分手部结构，实物核对时避免漏算或重复计入 |
| 执行器近似 | 使用力矩 motor，默认 armature、摩擦等采用统一参数 | 不能认定已还原电机、减速器、摩擦、温升及通信特性 |

固定躯干下的双臂重力矩主要取决于质量、重心、几何和重力方向；转动惯量主要影响动态运动。故现有模型足以开展静态补偿原型，但站立整机验证还要处理骨盆等模型差异。

已完成两类实验：原始模型三个姿态下，RNEA 重力矩与重心 Jacobian 求和交叉比较，最大误差约 `1.14e-13 N·m`；以及保留原始双臂动力学、固定躯干、去除碰撞接触的控制对照。后一实验物理频率 1000 Hz、控制频率 500 Hz，Kp=20、Kd=2，有初始肩肘角度偏差，每组运行 6 秒，最后一秒双臂角度 RMS 误差如下：

| 控制方式 | RMS 角度误差 |
| --- | ---: |
| PD，无重力前馈 | 7.956° |
| PD + 0.8 倍模型重力 | 1.477° |
| PD + 1.0 倍模型重力 | 0.108° |

这些实验验证的是标称模型下的计算与控制路径。它们没有调用交付 VR 控制器，没有验证 URS、ROS/HAL 闭环、真机参数或自由站立，也不能把上述误差视为真机性能承诺。

**四、如何在实机定位类似接口及内部补偿**

实机 URS 的位置控制已经确认有效，下一步重点是查清其下游实现与开放能力，而不是重新证明 URS 是否存在。建议先做只读检查，再决定是否需要受控对照。

**4.1 确认运行版本、接收节点及下游输出**

在加载了对应真机 ROS/AimDK 环境的终端，逐项执行：

```bash
ros2 run py_examples get_mc_action
ros2 topic info /mc/upper_body_command --verbose
ros2 node list
ros2 topic info /aima/hal/joint/arm/command --verbose
ros2 topic info /aima/hal/joint/arm/state --verbose
```

在用户已验证 URS 有效的控制过程中，记录上半身话题的接收节点、其下游 arm command 发布者、话题类型和 QoS。若接收节点使用不同名称，以实际运行图为准。`ros2 node info <实际节点名>` 可以继续查看服务、订阅和发布关系。对话题的发布/订阅检查方法参见 [ROS 2 官方说明](https://raw.githubusercontent.com/ros2/ros2_documentation/humble/source/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.rst)。

保存真机 SDK/MC 版本、实际进程可执行路径、启动参数、配置目录、机器人硬件版本、末端型号及软件包哈希。可从进程启动命令和服务启动配置定位文件，不应假设与本项目目录相同。`em_run.sh` 显示了本交付包如何区分 REAL/SIM 环境，但它不能证明真机也采用同样的启动方式。

需要分别确认“用户消息已被接收”“控制分支正在执行”“补偿进入最终命令”“执行器采用该命令”。订阅数量或函数初始化日志只覆盖其中一部分。

**4.2 检查真机配置、源码或动态库**

先在确认过的 MC 参数目录搜索：

```bash
# 将占位路径替换为实际运行配置目录。
rg -n -i 'gravity|gravcomp|compens|compense|feedforward|rnea|重力|补偿|UPPERBODY_REMOTE_SPLIT' \
  <实际MC配置目录> -g '*.yaml' -g '*.yml' -g '*.json'
```

有源码时，应沿“UpperBodyCommandArray 回调 → URS runner → 姿态规划 → 动力学/前馈 → HAL 命令输出”追踪，重点确认：

- 是否计算 `g(q)`、`rnea`、`computeGeneralizedGravity`，或者使用预先辨识的重力模型。
- 补偿开关、比例、分关节系数、负载参数及其默认值；是否支持运行时读取或调整。
- 模型文件及版本，补偿使用实际姿态还是目标姿态，是否考虑基座/胸部姿态及腰部角度。
- 输出是关节侧 N·m、驱动电流还是其他单位；是否叠加了摩擦、动态或负载补偿。
- URS 与 VR 是否共用该代码。不能从本仿真 VR 库的实现直接推断实机 URS 的实现。

只有动态库时，可以在离线副本上检查：

```bash
nm -D -C <实际控制器动态库> | rg -i 'rnea|gravity|compens|compense|upper|split'
strings <实际控制器动态库> | rg -i 'gravity|compens|compense|\.urdf|upper_body|remote_split'
```

符号命中可提供定位线索；没有命中不能证明无补偿，函数可能被内联、去符号或放在其他模块中。二进制检查不能代替运行验证。不建议在自由站立的真机实时控制进程上设置会暂停线程的调试断点。

**4.3 区分“内部已有补偿”与“开放可叠加接口”**

| 需要确认的能力 | 可采用的证据 | 与开发的关系 |
| --- | --- | --- |
| URS 内部已有自动重力补偿 | 源码、厂商说明、控制器调试变量、受控参数对照 | 通常优先复用或标定，避免重复叠加 |
| 可配置末端质量/重心或负载 | 已生效的配置、参数读取和负载对照 | 可能无需自行替换控制器 |
| 可在 URS 上叠加前馈力矩 | 明确的接口字段、仲裁规则、单位及生效测试 | 可保留下肢与现有上肢规划，仅增加前馈 |
| 可完整接管手臂 HAL | 支持关闭原手臂输出、明确的接管与退出机制 | 才能考虑独立手臂控制节点 |
| 只有上半身位置输入 | 已验证的位置 API，没有已确认的力矩/增益入口 | 不能直接从该消息传递物理意义的重力力矩 |

“没有公开补偿开关”“没有附加力矩字段”和“内部没有补偿”是不同结论。公开消息仅含位置，并不排除 MC 或驱动侧已经补偿。

**五、如何验证实机是否实际补偿**

**5.1 先记录现有 URS 的正常运行，不改变参数**

选取用户已验证可执行的、远离限位与碰撞的少量姿态，缓慢到位并静态保持。记录目标角、实际角、速度、命令 effort、反馈 effort/电流、增益、躯干/腰部姿态、负载及时间戳。优先获得 MC 内部独立的重力、摩擦、反馈力矩调试量；外部总 effort 未必能分解其来源。

本项目的 [record_arm_compensation.py](../tools/record_arm_compensation.py)仅订阅 arm command/state，可用于静态观测。上传到真机或开发机上实际可见的路径并加载 ROS/AimDK 环境后，运行：

```bash
python3 record_arm_compensation.py --output urs_baseline.csv --warmup 5 --seconds 15
```

它不发送控制命令，输出文件已存在时会拒绝覆盖。命令和状态采用最近收到的样本，并非严格同步；PD 与 effort+PD 列只是按标准模型估算，不是执行器实测力矩。脚本已检查语法与命令行入口，尚未在用户真机环境执行；消息类型、14 关节排列及 QoS 应以真机实际接口核对。50 Hz 的采样适合静态检查，不足以独立评估高频闭环稳定性。

**5.2 具备可靠参数入口后，再做受控 A/B 对照**

先确认补偿开关/比例属于正在运行的 URS 分支，以及参数是否支持热更新。若需重启 MC，按真机维护流程处理支撑与接管，不能照搬仿真中重启进程的做法。没有确认参数语义和恢复机制前，不直接套用本仿真的 `compense_ratio`。

在有可靠支撑或承托、可恢复的条件下，对同一组姿态比较不同补偿比例；若允许测试 0 与 0.8，可保持相同计算分支，仅改变比例。保持模型、负载、增益、目标轨迹等其他条件一致。两组的实际关节角、胸部/腰部姿态应接近，否则重力矩本身不同，不能直接按目标角比较力矩。

逐级建立证据：

| 观察 | 可以支持的判断 | 尚不能直接证明的内容 |
| --- | --- | --- |
| 活跃控制器的重力调试量随姿态变化 | 补偿计算在执行 | 已进入最终输出 |
| 改变比例后，最终命令对应力矩分量变化 | 参数影响控制输出 | 驱动已经按该值执行 |
| 执行器实际力矩/电流及姿态误差响应与预期一致 | 补偿对物理系统有作用 | 全工作空间和所有负载都适用 |

非零 effort 可能来自其他前馈；状态 effort 也可能包含反馈控制。补偿启用后总保持力矩不一定增加，因为位置反馈原本也承担支撑重力的任务。机器人站得住、手臂位置准确、消息持续发布，均不能单独证明重力补偿。

若力矩分量无法直接读取，应结合源码/厂商信息、多姿态模型预测和受控参数对照判断。缺少观测入口时应保留“未能证实”，不能用一次静态保持反推具体算法。

**5.3 上真机前必须核对的实际约束**

当前交付[底层关节文档](../aimdk/docs/cn/_build/html/zh-cn/dev/Interface/control_mod/joint_control.html)明确说明 `/aima/hal/joint/*/command` 没有超时或失效保护。实机 URS 高层入口可能有独立超时逻辑，应按实际版本核查，不能把高层保护自动等同于底层保护。

自主站立测试需要明确的手臂控制权、驱动/独立监督侧失效接管及可用急停。进程异常退出时，仅在同一进程里注册退出回调不能覆盖全部故障。是否保持、阻尼或由原 MC 接管取决于支撑状态，不能笼统要求全身清零力矩。模型电机限幅也不能直接视作真机持续工作额定力矩。

**六、若没有可用补偿接口，自行开发的可选路线**

这里的“没有”需先明确：究竟是内部没有重力补偿、没有用户可调参数，还是没有额外前馈/接管入口。不同情况对应不同开发范围。

| 路线 | 实现方式 | 必要条件 | 验证范围与主要限制 |
| --- | --- | --- | --- |
| A：获得匹配实机的仿真 MC | 使用与真机 URS 接口和控制逻辑匹配、可连接 MuJoCo HAL 的包 | 需确认厂商是否提供及兼容范围 | 最有利于复现真实控制路径；当前不能假设该包已经可获得 |
| B：在原 MC 内部增加或开放补偿 | 在 URS 的规划与 HAL 输出间增加 `g(q)` 或末端负载补偿 | 对应源码、可用 runner/plugin SDK 或厂商扩展支持 | 保留现有下肢与命令仲裁，适合最终集成；不能仅改 YAML 获得缺失实现 |
| C：通过已支持的附加力矩入口叠加 | 自定义计算器输出重力前馈，由 MC 仲裁并叠加 | 明确支持 additive effort、单位、增益及原补偿状态 | 改动较小；位置接口不能自动当作附加力矩接口，重复补偿需排除 |
| D：独立接管手臂 HAL | 下肢/腰部由 MC 平衡，上肢由自定义节点控制 | 原 MC 可明确停止手臂输出，具备接管/退出与独立失效保护 | 灵活，但须处理模型、实时性与全身耦合；两个发布者轮流覆盖不是仲裁方案 |
| E：固定躯干独立开发 | MuJoCo 固定基座双臂 → 支撑条件下真机双臂 | 可用的手臂控制入口及模型 | 当前最容易推进算法验证；不能替代自由站立整机验证 |
| F：仅位置接口下的外环修正 | 在位置目标上增加经标定、限幅、缓变的偏置 | 内环行为和有效刚度足够明确，厂商允许该用法 | 可改善静态误差，但不是直接力矩前馈；不能保证透明拖动或准确抵消重力 |

路线 F 中，若内环近似为已知刚度 Kp 的位置伺服，角度偏置产生的附加力矩可局部近似为 `Kp * delta_q`。但实际内环可能有积分、非线性、已有重力补偿及隐藏限幅，因此不能直接把 `delta_q = g(q)/Kp` 当作通用控制律；它只适合作为条件明确时的外环方案。

对 B/C/D/E 的第一版实现，可先采用带位置保持和阻尼的控制律：

```text
tau_command = alpha * g_hat(q, torso_orientation, payload)
              + Kp * (q_ref - q)
              + Kd * (qdot_ref - qdot)
```

随后统一施加经确认的关节力矩限幅、变化率限制和故障接管。重力前馈依据模型直接提供预计支撑力矩，使控制器不必完全依靠位置误差抵抗重力；反馈项用于纠偏和阻尼。纯重力项不会消除摩擦，也不会自行限制速度或保证平衡。

计算器可使用 Pinocchio 的广义重力接口，或在独立 MuJoCo 计算 data 中令速度为零计算重力项。运动状态下的 MuJoCo `qfrc_bias` 还包括科氏、离心项，不能直接当作纯重力，参见 [MuJoCo 动力学定义](https://mujoco.readthedocs.io/en/3.3.7/computation/index.html#general-framework)。模型自由度与 HAL 固定关节顺序必须显式映射；浮动基座的六个广义力不是可下发的六个电机力矩。

站立时应计入胸部/基座与腰部姿态。双臂移动会改变整机重心及作用于躯干的反作用力，下肢控制器能否适应需要额外测试，不能从“手臂重力矩正确”推断“整机稳定”。

**七、建议推进顺序**

1. 以用户已验证有效的真机 URS 为入口，记录版本、节点、配置、实际下游命令；确认内部补偿、负载参数和扩展接口，避免先开发一份重复补偿。
2. 确认是否可获得同版本仿真 MC。若有，优先对齐接口、模型和控制逻辑；若无，选择 B/C/D 中具备明确支持条件的一条作为最终接入路线。
3. 同步推进 E：统一双臂模型、末端质量/重心、零点和重力方向，完成固定躯干的多姿态、低速轨迹及模型误差实验。
4. 在支撑条件下核对真机力矩/电流映射与重力模型，用独立保留姿态评估误差，再平滑启用补偿和测试退出接管。
5. 最后做“下半身稳定站立＋上半身控制”的整体验证，覆盖姿态、负载、饱和、温升、通信失效和控制器接管。验收阈值依据具体硬件与任务制定。

如果当前可用条件只有已验证的 URS 位置接口和本项目交付包，则可以继续模型与固定躯干实验；尚不能保证能在闭源 MC 外直接接入一个独立的站立上肢力矩控制器。
